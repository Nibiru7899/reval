# ADR 0005 — Snapshots are committed as `reval.lock.json`

- **Status:** accepted
- **Date:** 2026-10-24

## Context
Datasets and trained models are git-ignored (too large; regenerated by scripts). `reval diff A B` must still compare the project
state at two git revisions, including field-level hashes of artifacts that aren't in git.

## Decision
`reval snapshot --write` serializes the complete `Snapshot` (manifest entities, artifact versions with field hashes, field values,
and row-group bounding boxes, plus producer metadata and code hashes) to `reval.lock.json` at the project root. It is deterministic:
sorted keys, no timestamps, 2-space indent, LF line endings. Users commit it, the same way they commit `poetry.lock` or `dvc.lock`.

- `reval diff A B` reads `reval.lock.json` at each revision via `git show REV:reval.lock.json`. No checkout or worktree is needed.
- `reval diff` with one revision compares that revision's lock against the working tree (computed live).
- `reval status` warns (exit code 3 with `--strict`) if the working tree differs from the committed lock.
- The snapshot id is the SHA-256 of the canonical JSON of the snapshot without its `id` field.

## Consequences
- Fast diffs between any two commits, and the benchmark can build scenarios as plain commits.
- The lock grows with dataset group count × columns (~1k entries for the motor dataset, roughly 100–300 KB). That's acceptable.
- A stale lock (data changed, lock not rewritten) is detected by comparing live hashes against the lock. CI should run `reval snapshot --check`.
